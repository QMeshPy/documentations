This page lists what is **not** in `main` yet, as of **1 November 2026**. It comes from the open pull requests and issues of
[QMeshPy/distributed-quantum](https://github.com/QMeshPy/distributed-quantum). The maintainers call the plan a proposal,
and the epic ([#1](https://github.com/QMeshPy/distributed-quantum/issues/1)) sets these ground rules for all of it:

- **Testnet first.** No mainnet code path is turned on without an explicit maintainer decision.
- **No secrets** in the repository, logs, prompts or browser bundles.
- **Chain logic stays behind the chain registry.**
- **The platform runs on simulators.** No feature is described as running on quantum hardware.

What already shipped is on the [integrations overview](/docs/integrations/overview).

## Proposed: the content layer

The epic [#43](https://github.com/QMeshPy/distributed-quantum/issues/43) covers Helia in the browser, Kubo as the platform node
and Boxo where needed. Open items include draining the pin retry queue ([#44](https://github.com/QMeshPy/distributed-quantum/issues/44)),
a server-side pinning broker ([#45](https://github.com/QMeshPy/distributed-quantum/issues/45) and
[#46](https://github.com/QMeshPy/distributed-quantum/issues/46)), pinning as a CAR
([#48](https://github.com/QMeshPy/distributed-quantum/issues/48)), versioned record schemas
([#50](https://github.com/QMeshPy/distributed-quantum/issues/50)), export and import as a CAR
([#52](https://github.com/QMeshPy/distributed-quantum/issues/52)), several spikes (one Helia node per browser, large artefacts,
IPNS feeds, Kubo pubsub bridged to GossipSub), a CID allowlist and takedown denylist
([#72](https://github.com/QMeshPy/distributed-quantum/issues/72)) and an IPFS adapter for provenance verification
([#74](https://github.com/QMeshPy/distributed-quantum/issues/74)).
